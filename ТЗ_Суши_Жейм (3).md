# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Веб-приложение для доставки паназиатской кухни «СУШИ ЖЕЙМ»

**Проект:** онлайн-сервис заказа еды  
**Формат:** web-приложение  
**Основные роли:** Пользователь, Администратор  
**Frontend:** Next.js  
**Backend:** TypeScript  
**AI:** OpenAI, Gemini  
**DB:** PostgreSQL, Redis  
**Storage:** S3  
**Версия ТЗ:** 1.0  
**Дата:** 08.09.2026

- 1.3. Идея проекта
Идея заключается в объединении каталога паназиатских блюд, корзины, оформления заказа, доставки и административной панели в одном сервисе. Интерфейс должен быть адаптирован под мобильные устройства и компьютер.

- 1.4. Бизнес-задачи
Увеличение количества онлайн-заказов.

Снижение нагрузки на операторов при приёме заказов.

Централизованное управление меню и ценами.

Ускорение обработки заказов.

Повышение удобства повторных заказов.

Формирование базы статистики по продажам и популярности блюд.

- 1.5. Принципы продукта
Простота — основные действия доступны без лишних переходов.

Скорость — страницы и каталог должны загружаться быстро.

Прозрачность — пользователь всегда видит состав заказа и итоговую стоимость.

Надёжность — данные заказа должны сохраняться корректно.

Адаптивность — интерфейс должен работать на смартфонах, планшетах и ПК.


## 2. Целевая аудитория

Основная аудитория — люди, которые заказывают готовую еду через интернет и ценят скорость, понятное меню, удобную доставку и возможность быстро повторить заказ.

## 6. Логика работы приложения

- 6.1. Общая логика
Пользователь открывает сайт → просматривает меню → выбирает товары → добавляет их в корзину → изменяет количество → переходит к оформлению → вводит данные → подтверждает заказ → сервер валидирует данные → создаётся заказ → пользователь получает подтверждение → администратор обрабатывает заказ → статус обновляется.

- 6.2. Логика корзины
При добавлении товара система проверяет его наличие и доступность.

Если товар уже находится в корзине, количество увеличивается.

При уменьшении количества до нуля товар удаляется.

Стоимость позиции рассчитывается как цена × количество.

Итоговая стоимость рассчитывается на сервере перед созданием заказа.

Итоговая сумма дополнительно проверяется сервером перед созданием заказа.

- 6.3. Логика заказа
Сервер получает состав корзины и данные доставки.

Система повторно получает актуальные цены товаров из БД.

Проверяется доступность товаров.

Рассчитывается сумма заказа и доставка.

Создаётся запись заказа и его позиций.

Заказ получает статус «Новый».

Администратор видит заказ в панели.

- 6.4. Отмена
Если бизнес-правила разрешают отмену, пользователь может отменить заказ только на определённых этапах. После передачи в доставку отмена может быть запрещена или передана на ручное решение администратора.

## 8. AI-функциональность

- 8.1. Общая концепция
AI используется как дополнительная функция: для рекомендаций, поиска и помощи с текстами. Основные данные о товарах и заказах хранятся в системе.

- 8.2. OpenAI
AI-помощник по меню: отвечает на вопросы о блюдах на основе данных каталога.

Рекомендации блюд по запросу пользователя.

Формирование текстовых описаний товаров для администратора.

Классификация или нормализация текстовых запросов поиска.

Помощь оператору при обработке типовых вопросов.

- 8.3. Gemini
Альтернативный AI-провайдер для рекомендаций и обработки текстовых запросов.

Анализ пользовательских запросов по меню.

Генерация черновиков контента.

Резервный AI-провайдер при проектировании multi-provider архитектуры.

- 8.4. Ограничения AI
AI не изменяет цены и статусы заказов самостоятельно. Эти данные меняет администратор.

AI не должен получать лишние персональные данные.

Ответы должны формироваться на основе разрешённого контекста.

Если AI не может точно ответить, пользователь должен получить понятное сообщение об этом.

- 8.5. Архитектура AI
Frontend отправляет запрос на Backend. Backend определяет тип запроса, при необходимости получает данные из PostgreSQL/Redis, формирует контекст и обращается к выбранному AI-провайдеру. Ответ проходит базовую валидацию и возвращается пользователю.


## 9. Технологический стек и архитектура

- 9.1. Frontend — Next.js
Для клиентской части используется Next.js. Он отвечает за страницы, компоненты интерфейса, маршрутизацию, серверный рендеринг/статическую генерацию там, где это целесообразно, а также адаптивную структуру приложения.

- 9.2. Backend — TypeScript
Серверная логика реализуется на TypeScript. Backend отвечает за API, бизнес-правила, авторизацию, расчёт заказов, работу с БД, кешем, хранилищем и AI.

- 9.3. AI — OpenAI и Gemini
Используются два AI-провайдера. Интеграцию рекомендуется отделить от бизнес-логики через единый внутренний интерфейс AI-сервиса.

- 9.4. PostgreSQL
Пользователи.

Роли.

Товары.

Категории.

Заказы.

Позиции заказов.

Адреса.

Промокоды.

Настройки доставки.

Логи и необходимые служебные данные.

- 9.5. Redis
Кеш популярных/часто запрашиваемых данных.

Сессии и временные данные при выбранной архитектуре.

Rate limiting.

Короткоживущие статусы и технические блокировки.

Очереди фоновых задач — если будет добавлен соответствующий механизм.

- 9.6. S3
S3 используется как объектное хранилище для изображений блюд, баннеров и других файлов. В PostgreSQL сохраняются ссылки и метаданные, а не сами большие бинарные файлы.

- 9.7. Общая схема
Next.js → Backend на TypeScript → PostgreSQL / Redis / S3 / OpenAI / Gemini.


## 10. Структура данных и API


### 10.1. Основные сущности

User: id, name, phone/email, role, createdAt.

Category: id, name, slug, sortOrder, isActive.

Product: id, categoryId, name, description, price, imageUrl, weight, isAvailable.

Order: id, userId, status, subtotal, deliveryCost, total, address, comment, createdAt.

OrderItem: id, orderId, productId, productNameSnapshot, priceSnapshot, quantity.

Address: id, userId, title, address, comment.

PromoCode: id, code, type, value, activeFrom, activeTo, isActive.


### 10.2. Почему нужны snapshot-поля в OrderItem

Название и цена товара на момент заказа должны сохраняться отдельно. Если администратор позже изменит название или цену, старый заказ должен отображаться с теми данными, которые были актуальны при оформлении.


### 10.3. Пример API-разделов

GET /api/categories — список категорий.

GET /api/products — каталог товаров.

GET /api/products/:id — карточка товара.

POST /api/cart/validate — проверка состава корзины перед заказом.

POST /api/orders — создание заказа.

GET /api/orders/:id — получение заказа.

GET /api/profile/orders — история заказов.

POST /api/admin/products — создание товара.

PATCH /api/admin/products/:id — изменение товара.

PATCH /api/admin/orders/:id/status — изменение статуса.


### 10.4. Валидация

Данные заказа проверяются перед сохранением, чтобы избежать ошибок.
