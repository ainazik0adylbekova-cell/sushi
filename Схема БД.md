# 1. Пользователи — `users`

Таблица `users` предназначена для хранения информации обо всех зарегистрированных пользователях системы.

Каждый пользователь получает собственную учётную запись. Через эту таблицу приложение может определить, кто оформил заказ, кому принадлежит адрес или корзина, а также какая роль назначена пользователю.

| Поле         | Тип          | Что хранит                            |
| ------------ | ------------ | ------------------------------------- |
| `id`         | UUID         | Уникальный идентификатор пользователя |
| `name`       | VARCHAR(100) | Имя пользователя                      |
| `phone`      | VARCHAR(20)  | Номер телефона пользователя           |
| `email`      | VARCHAR(255) | Электронная почта                     |
| `password`   | VARCHAR(255) | Пароль в защищённом виде              |
| `role_id`    | UUID         | Ссылка на роль пользователя           |
| `is_active`  | BOOLEAN      | Активен ли аккаунт                    |
| `created_at` | TIMESTAMP    | Дата и время регистрации              |

### Описание полей

**`id`** — уникальный номер пользователя. Он используется для связи пользователя с другими таблицами, например с заказами, адресами и корзиной.

**`name`** — имя пользователя, которое вводится при регистрации.

**`phone`** — номер телефона. Он может использоваться для связи с клиентом по поводу заказа.

**`email`** — электронная почта пользователя. Используется для регистрации, авторизации или дополнительной связи.

**`password`** — пароль пользователя. В базе данных пароль должен храниться не в открытом виде, а в виде защищённого хеша.

**`role_id`** — определяет права пользователя в системе. Через это поле пользователь связывается с таблицей `roles`.

**`is_active`** — показывает, активна ли учётная запись. Администратор может отключить аккаунт без полного удаления его данных.

**`created_at`** — дата и время создания аккаунта.

### Пример

Пользователь:

* Имя: Айназик
* Телефон: +996 XXX XXX XXX
* Email: [user@example.com](mailto:user@example.com)
* Роль: Пользователь
* Аккаунт: активен

# 2. Роли — `roles`

Таблица `roles` хранит список доступных ролей пользователей.

Роли необходимы для разграничения доступа к функциям приложения. Например, обычный пользователь не должен иметь доступ к административной панели.

| Поле          | Тип         | Что хранит              |
| ------------- | ----------- | ----------------------- |
| `id`          | UUID        | Уникальный ID роли      |
| `name`        | VARCHAR(50) | Название роли           |
| `description` | TEXT        | Подробное описание роли |

### Основные роли

В проекте используются две основные роли:

### Пользователь

Пользователь может:

* просматривать меню;
* открывать информацию о товарах;
* добавлять блюда в корзину;
* изменять количество товаров;
* удалять товары из корзины;
* указывать адрес доставки;
* оформлять заказ;
* выбирать способ оплаты;
* использовать промокоды;
* просматривать информацию о своих заказах.

### Администратор

Администратор может:

* управлять товарами;
* добавлять и изменять категории;
* изменять цены;
* управлять доступностью товаров;
* просматривать заказы;
* изменять статусы заказов;
* управлять доставкой;
* работать с промокодами;
* просматривать действия администраторов.

Связь между `roles` и `users` позволяет одному типу роли быть назначенным нескольким пользователям.

# 3. Категории — `categories`

Таблица `categories` предназначена для хранения категорий меню.

Категории позволяют удобно разделить товары по типам блюд и сделать меню более понятным для пользователя.

| Поле          | Тип          | Что хранит                      |
| ------------- | ------------ | ------------------------------- |
| `id`          | UUID         | Уникальный ID категории         |
| `name`        | VARCHAR(100) | Название категории              |
| `description` | TEXT         | Описание категории              |
| `image_url`   | TEXT         | Ссылка на изображение категории |
| `sort_order`  | INTEGER      | Порядок отображения категории   |
| `is_active`   | BOOLEAN      | Показывать категорию или нет    |

### Примеры категорий

* Роллы
* Суши
* Сеты
* Вок
* Напитки

### Назначение полей

`sort_order` используется для определения порядка категорий в меню. Например, сначала могут отображаться «Роллы», затем «Суши», «Сеты», «Вок» и «Напитки».

`is_active` позволяет временно скрыть категорию, не удаляя её из базы данных.

# 4. Товары — `products`

Таблица `products` является одной из основных таблиц проекта. Она содержит информацию обо всех блюдах, которые пользователь может увидеть в меню и заказать.

Каждый товар относится к определённой категории.

| Поле           | Тип           | Что хранит                |
| -------------- | ------------- | ------------------------- |
| `id`           | UUID          | Уникальный ID блюда       |
| `category_id`  | UUID          | Ссылка на категорию       |
| `name`         | VARCHAR(200)  | Название блюда            |
| `description`  | TEXT          | Описание блюда            |
| `price`        | NUMERIC(10,2) | Цена блюда                |
| `weight`       | NUMERIC(8,2)  | Вес блюда                 |
| `pieces_count` | INTEGER       | Количество штук           |
| `image_url`    | TEXT          | Ссылка на изображение     |
| `is_available` | BOOLEAN       | Доступно ли блюдо         |
| `created_at`   | TIMESTAMP     | Дата добавления           |
| `updated_at`   | TIMESTAMP     | Дата последнего изменения |

### Пример товара

**Филадельфия**

* Категория: Роллы
* Цена: 650 сом
* Вес: 280 г
* Количество: например, 8 штук
* Доступность: да

### Работа с товарами

Администратор может добавлять новые блюда, изменять их описание, цену, изображение и доступность.

Если определённого блюда временно нет в наличии, его можно сделать недоступным через `is_available`, не удаляя товар из базы.

Это особенно важно для истории заказов, поскольку старые заказы должны сохранять информацию о товарах, даже если эти товары позже были удалены или изменены.

# 6. Корзины — `carts`

Таблица `carts` предназначена для хранения информации о корзинах пользователей.

Корзина является временным местом хранения товаров, которые пользователь хочет приобрести.

| Поле         | Тип       | Что хранит                                 |
| ------------ | --------- | ------------------------------------------ |
| `id`         | UUID      | Уникальный ID корзины                      |
| `user_id`    | UUID      | Пользователь, которому принадлежит корзина |
| `created_at` | TIMESTAMP | Дата создания корзины                      |
| `updated_at` | TIMESTAMP | Дата последнего изменения                  |

У пользователя может быть корзина, связанная с его аккаунтом.

Когда пользователь добавляет блюдо в корзину, сама информация о товаре хранится в таблице `cart_items`.

# 7. Товары в корзине — `cart_items`

Таблица `cart_items` хранит конкретные товары, которые находятся в корзине.

| Поле         | Тип       | Что хранит            |
| ------------ | --------- | --------------------- |
| `id`         | UUID      | Уникальный ID позиции |
| `cart_id`    | UUID      | Ссылка на корзину     |
| `product_id` | UUID      | Ссылка на товар       |
| `quantity`   | INTEGER   | Количество товара     |
| `created_at` | TIMESTAMP | Дата добавления       |

### Работа корзины

Если пользователь нажимает кнопку **«+»**, значение `quantity` увеличивается.

Если пользователь нажимает кнопку **«−»**, количество уменьшается.

Если количество товара становится равным нулю, товар может быть удалён из корзины.

### Пример

| Блюдо       | Количество |
| ----------- | ---------: |
| Филадельфия |          2 |
| Вок         |          1 |

В этом случае таблица `cart_items` будет содержать две позиции, связанные с одной корзиной.

# 8. Заказы — `orders`

Таблица `orders` хранит основную информацию об оформленных заказах.

Когда пользователь переходит от корзины к оформлению заказа, создаётся новая запись в таблице `orders`.

| Поле            | Тип           | Что хранит                    |
| --------------- | ------------- | ----------------------------- |
| `id`            | UUID          | Уникальный ID заказа          |
| `order_number`  | VARCHAR(30)   | Номер заказа                  |
| `user_id`       | UUID          | Пользователь, создавший заказ |
| `status_id`     | UUID          | Текущий статус заказа         |
| `address`       | TEXT          | Адрес доставки                |
| `comment`       | TEXT          | Комментарий клиента           |
| `subtotal`      | NUMERIC(10,2) | Сумма товаров                 |
| `delivery_cost` | NUMERIC(10,2) | Стоимость доставки            |
| `discount`      | NUMERIC(10,2) | Размер скидки                 |
| `total`         | NUMERIC(10,2) | Итоговая стоимость            |
| `created_at`    | TIMESTAMP     | Дата создания заказа          |

### Расчёт заказа

Например:

* Стоимость товаров: 1500 сом
* Доставка: 150 сом
* Скидка: 100 сом
* Итоговая сумма: 1550 сом

Формула:

**1500 + 150 − 100 = 1550 сом**

`order_number` нужен для удобного отображения заказа пользователю и администратору.

Например:

**Заказ №10025**

# 9. Товары заказа — `order_items`

Таблица `order_items` содержит список конкретных товаров, которые входят в заказ.

| Поле           | Тип           | Что хранит                       |
| -------------- | ------------- | -------------------------------- |
| `id`           | UUID          | Уникальный ID позиции            |
| `order_id`     | UUID          | Ссылка на заказ                  |
| `product_id`   | UUID          | Ссылка на товар                  |
| `product_name` | VARCHAR(200)  | Название товара на момент заказа |
| `price`        | NUMERIC(10,2) | Цена товара на момент заказа     |
| `quantity`     | INTEGER       | Количество товара                |
| `subtotal`     | NUMERIC(10,2) | Общая стоимость позиции          |

### Почему название и цена сохраняются отдельно?

Это необходимо для сохранения истории заказов.

Например, сегодня «Филадельфия» стоит 650 сом, а через несколько месяцев администратор изменит цену на 700 сом.

Старый заказ пользователя не должен автоматически измениться.

Поэтому в `order_items` сохраняются:

* название товара на момент заказа;
* цена товара на момент заказа;
* количество;
* итоговая сумма позиции.

Таким образом, история заказа остаётся корректной.

# 10. Статусы заказов — `order_statuses`

Таблица `order_statuses` хранит возможные состояния заказа.

| Поле          | Тип         | Что хранит            |
| ------------- | ----------- | --------------------- |
| `id`          | UUID        | Уникальный ID статуса |
| `name`        | VARCHAR(50) | Название статуса      |
| `description` | TEXT        | Описание статуса      |

### Основные статусы

1. **Новый** — заказ только что создан.
2. **Подтверждён** — заказ принят и подтверждён.
3. **Готовится** — ресторан начал готовить заказ.
4. **Передан в доставку** — заказ передан курьеру.
5. **Доставлен** — заказ успешно доставлен.
6. **Отменён** — заказ был отменён.

Статус позволяет пользователю видеть, на каком этапе находится его заказ.

Администратор может изменять статус заказа в административной панели.

# 15. Промокоды — `promo_codes`

Таблица `promo_codes` предназначена для хранения промокодов и условий их использования.

Промокоды позволяют предоставлять пользователям скидки.

Таблица `admin_action_logs` предназначена для хранения истории действий администратора.

| Поле          | Тип          | Что хранит                      |

### Примеры действий

Администратор:

* добавил новый товар;
* изменил цену;
* изменил описание блюда;
* отключил товар;
* добавил категорию;
* изменил статус заказа;
* создал промокод;
* изменил условия доставки.

### Пример записи

**Администратор изменил цену товара «Филадельфия».**

В журнале сохраняется:

* ID администратора;
* действие — изменение цены;
* объект — товар;
* ID товара;
* дата и время изменения.

# Связи между таблицами

Все таблицы базы данных связаны между собой с помощью идентификаторов.

Общая структура связей выглядит следующим образом:

```text
ROLES
  ↓
USERS
  ├── ADDRESSES
  │
  ├── CARTS
  │     ↓
  │   CART_ITEMS
  │      ↓
  │   PRODUCTS
  │      ↑
  │  CATEGORIES
  │
  └── ORDERS
        ├── ORDER_ITEMS
        │      ↓
        │   PRODUCTS
        │
        ├── ORDER_STATUSES
        │
        ├── ORDER_STATUS_HISTORY
        │
        ├── PAYMENTS
        │      ↓
        │   PAYMENT_METHODS
        │
        ├── ORDER_PROMOS
        │      ↓
        │   PROMO_CODES
        │
        └── DELIVERY_ZONES

USERS
  ↓
ADMIN_ACTION_LOGS
```

---

# Подробное описание основных связей

## `roles` → `users`

Одна роль может быть назначена нескольким пользователям.

Например:

```text
Роль «Пользователь»
    ↓
Айназик
Другой пользователь
Ещё один пользователь
```

Каждый пользователь хранит `role_id`, который указывает на соответствующую роль.

---

## `users` → `addresses`

Один пользователь может иметь несколько адресов.

```text
Пользователь
    ├── Дом
    ├── Работа
    └── Другой адрес
```

Каждый адрес содержит `user_id`, который показывает, кому он принадлежит.

---

## `users` → `carts`

Корзина связана с конкретным пользователем.

```text
Пользователь
    ↓
Корзина
```

Благодаря этому приложение понимает, какие товары находятся в корзине конкретного пользователя.

---

## `carts` → `cart_items`

Одна корзина может содержать несколько позиций.

```text
Корзина
  ├── Филадельфия × 2
  ├── Вок × 1
  └── Напиток × 2
```

`cart_items` хранит количество каждого товара.

---

## `categories` → `products`

Одна категория может содержать множество товаров.

Например:

```text
Роллы
  ├── Филадельфия
  ├── Калифорния
  └── Дракон
```

Каждый товар содержит `category_id`.

---

## `users` → `orders`

Один пользователь может оформить несколько заказов.

```text
Айназик
  ├── Заказ №10001
  ├── Заказ №10025
  └── Заказ №10050
```

Поле `user_id` в таблице `orders` определяет владельца заказа.

---

## `orders` → `order_items`

Один заказ может содержать несколько товаров.

```text
Заказ №10025
  ├── Филадельфия × 2
  ├── Вок × 1
  └── Напиток × 2
```

Таблица `order_items` хранит отдельные позиции заказа.

---

## `orders` → `order_statuses`

Каждый заказ имеет текущий статус.

Например:

```text
Заказ №10025
       ↓
   Готовится
```

Поле `status_id` связывает заказ с таблицей статусов.

---

## `orders` → `order_status_history`

История позволяет хранить все изменения статуса одного заказа.

```text
Новый
  ↓
Подтверждён
  ↓
Готовится
  ↓
Передан в доставку
  ↓
Доставлен
```

Таким образом, приложение может показать пользователю весь процесс обработки заказа.

---

## `orders` → `payments`

Каждая оплата связана с определённым заказом.

```text
Заказ №10025
      ↓
Оплата
      ↓
1550 сом
```

---

## `payments` → `payment_methods`

Оплата также связана с выбранным способом оплаты.

```text
Оплата
   ↓
Банковская карта
```

или

```text
Оплата
   ↓
Наличные
```

---

## `orders` → `order_promos`

Если пользователь использовал промокод, информация о нём связывается с заказом.

```text
Заказ №10025
      ↓
   SUSHI10
      ↓
Скидка 100 сом
```

---

## `order_promos` → `promo_codes`

Таблица `order_promos` показывает, какой именно промокод был использован.

Это позволяет сохранять историю применения скидок.

---

## `orders` → `delivery_zones`

При оформлении заказа определяется зона доставки и соответствующие условия.

Зона может определять:

* стоимость доставки;
* минимальную сумму заказа;
* сумму для бесплатной доставки;
* доступность зоны.

---

## `users` → `admin_action_logs`

Если пользователь является администратором и выполняет действие в административной панели, информация об этом действии может сохраняться в журнале.

Например:

```text
Администратор
     ↓
Изменил цену товара
     ↓
Филадельфия
     ↓
Дата и время
```

---

# Общая логика работы базы данных

Работу базы данных проекта можно представить в виде последовательности действий пользователя.

### 1. Регистрация

Пользователь создаёт аккаунт.

В таблице `users` сохраняются:

* имя;
* телефон;
* email;
* защищённый пароль;
* роль;
* дата регистрации.

---

### 2. Просмотр меню

Пользователь открывает меню.

Приложение получает категории из `categories`, а товары — из `products`.

Например:

```text
Роллы
  ├── Филадельфия — 650 сом
  ├── Калифорния — 600 сом
  └── Дракон — 750 сом
```

---

### 3. Добавление товара в корзину

Пользователь нажимает кнопку добавления товара.

Создаётся или используется корзина в `carts`.

Сам товар добавляется в `cart_items`.

Например:

```text
Филадельфия × 2
```

Количество хранится в поле `quantity`.

---

### 4. Изменение корзины

Пользователь может изменить количество товара.

Кнопка:

```text
−  2  +
```

изменяет значение `quantity`.

Также пользователь может удалить товар из корзины.

---

### 5. Оформление заказа

После подтверждения корзины создаётся запись в `orders`.

В заказе сохраняются:

* пользователь;
* номер заказа;
* адрес;
* комментарий;
* сумма товаров;
* стоимость доставки;
* скидка;
* итоговая сумма;
* текущий статус.

---

### 6. Сохранение товаров заказа

Все товары из корзины переносятся в `order_items`.

При этом сохраняются название и цена товара на момент оформления заказа.

Это позволяет не потерять историю даже после изменения информации о товаре.

---

### 7. Выбор оплаты

Пользователь выбирает способ оплаты.

Данные сохраняются в `payments`.

Например:

```text
Заказ №10025
     ↓
Банковская карта
     ↓
1550 сом
```

---

### 8. Обработка заказа

После оформления заказ получает статус:

**Новый**

Администратор может изменить его на:

```text
Новый
   ↓
Подтверждён
   ↓
Готовится
   ↓
Передан в доставку
   ↓
Доставлен
```

Каждое изменение может сохраняться в `order_status_history`.

---

### 9. Использование промокода

Если пользователь вводит промокод, приложение проверяет:

* существует ли такой код;
* активен ли он;
* не закончился ли срок действия;
* соответствует ли сумма заказа минимальному условию.

После успешного применения скидка сохраняется в заказе.

---

### 10. Работа администратора

Администратор получает доступ к административной части системы.

Он может:

* добавлять товары;
* редактировать товары;
* изменять цены;
* менять доступность товаров;
* управлять категориями;
* просматривать заказы;
* изменять статусы;
* управлять промокодами;
* управлять условиями доставки.

Важные действия администратора могут сохраняться в `admin_action_logs`.

---

# Итоговая структура базы данных

В проекте используется **17 основных таблиц**:

1. `users` — пользователи;
2. `roles` — роли;
3. `categories` — категории меню;
4. `products` — товары;
5. `addresses` — адреса пользователей;
6. `carts` — корзины;
7. `cart_items` — товары в корзинах;
8. `orders` — заказы;
9. `order_items` — товары заказов;
10. `order_statuses` — статусы заказов;
11. `order_status_history` — история изменения статусов;
12. `delivery_zones` — зоны доставки;
13. `payment_methods` — способы оплаты;
14. `payments` — информация об оплатах;
15. `promo_codes` — промокоды;
16. `order_promos` — промокоды, использованные в заказах;
17. `admin_action_logs` — журнал действий администратора.

Такая структура позволяет разделить данные по назначению и установить между ними понятные связи. Пользователь, товары, корзина, заказы, доставка, оплата и административная часть работают как связанные элементы одной системы.

Главная цепочка работы выглядит следующим образом:

```text
ПОЛЬЗОВАТЕЛЬ
     ↓
КАТАЛОГ
     ↓
ТОВАРЫ
     ↓
КОРЗИНА
     ↓
ОФОРМЛЕНИЕ ЗАКАЗА
     ↓
ОПЛАТА
     ↓
ЗАКАЗ
     ↓
ПРИГОТОВЛЕНИЕ
     ↓
ДОСТАВКА
     ↓
ПОЛУЧЕНИЕ ЗАКАЗА
```

При этом администратор контролирует основные процессы через административную панель:

```text
АДМИНИСТРАТОР
     ├── Товары
     ├── Категории
     ├── Заказы
     ├── Статусы
     ├── Доставка
     ├── Оплата
     ├── Промокоды
     └── Журнал действий
```

Таким образом, база данных поддерживает основные функции проекта «Суши Жейм» и обеспечивает хранение информации о пользователях, меню, товарах, корзинах, заказах, доставке, оплате и работе администратора.
